Chapter Overview

This chapter explores a glitch in QuantLib when using curves with different day-count conventions. The problem occurs when pricing options with finite-difference engines that don't properly account for different day-count conventions between risk-free rate and volatility curves.

The Problem

When pricing options with different day-count conventions for risk-free rates and volatility curves, the analytic and finite-difference engines produce significantly different results. This is due to an implementation artifact where the FD engine uses a single time grid based on the risk-free rate convention, while the analytic engine can properly account for different conventions.

Key Insight

The finite-difference engine asks the volatility curve for the volatility at the exercise date and uses it on a time grid that follows the day-count convention of the risk-free rate, resulting in inconsistent time-to-maturity calculations.

Engine Behavior Comparison

Analytic Engine

Behavior: Properly accounts for different day-count conventions

  • Uses correct variance calculation
  • Accounts for volatility curve convention
  • Consistent with market practice
Finite-Difference Engine

Behavior: Uses single time grid, ignores volatility convention

  • Forced to use risk-free rate convention
  • Inconsistent variance calculation
  • Implementation artifact

Day-Count Convention Impact

Actual/365 Fixed

Used for risk-free rate curve

  • • T_grid = 0.25205479452054796
  • • Standard convention
  • • Used in time grid
Business/252

Used for volatility curve

  • • T_vol = 0.25793650793650796
  • • Market practice
  • • Ignored by FD engine
Variance Impact

Different calculations

  • • vol² × T_grid = 0.010082
  • • Correct variance = 0.010317
  • • Significant difference

Workaround Solution

To work around this issue, you can calculate a synthetic volatility that, when used with the day-count convention of the time grid, gives the correct variance:

vol_synthetic = sqrt(correct_variance / T_grid)

This synthetic volatility can then be used to build a volatility curve with the same day-count convention as the risk-free rate, allowing the FD engine to return more accurate results.

Important Note

This workaround becomes more complex with non-flat volatility curves, requiring conversion of multiple values or sampling and conversion for interpolated curves.

Best Practices

  • Sanity Checks: Always compare results between analytic and FD engines when possible
  • Convention Consistency: Use the same day-count convention for all curves when possible
  • Variance Verification: Verify that variance calculations are consistent across engines
  • Documentation: Document any workarounds and their implications for future reference
